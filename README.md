# 藏丘库务 · 库房除湿班前计划

用交班湿度推算下一班库房巡查顺序

模拟团队为 藏丘市档案服务站的 12 位保管与设施人员按三班轮值，地下层设有 6 个分别记录湿度的馆藏库房。。保管员每到 00:00、08:00 和 16:00 抄录库内外湿度和本班累计开门分钟。班长在下一班开始时照当天读值和经验决定巡查顺序。

- 只按当前湿度排序，开门频繁或室外持续潮湿的库房可能在下一班突然升到阈值。
- 同一时间抄录多个库房，随手切分记录会把同一班次的湿度变化同时用于拟合和评估。
- 湿度计断抄时用前值补齐会人为压低误差，班长无法分辨数据缺口与真实平稳。

三班交接记录、库房内外相对湿度与当班开门时长 设施班长按预测队列分配驻点巡查人手，值班员现场复测并回填读数

## 业务模块

| 模块 | 工作内容 | 核心实体 |
|---|---|---|
| 交班湿度簿 | CSV 校验、预览实测字段、以完整数据内容的 SHA-256 去重、追溯版本和下载原始数据 | 数据版本 |
| 班前湿度预测 | 按版本与领域参数创建计算单，由独立进程计算；从排队、成功或失败状态追溯 | 计算单 |
| 下一班巡查顺序 | 按业务字段查看度量、比较与排序，下载计算结果 | 计算单及其结果 |
| 库房巡查签交 | 对结果样本作签发或暂缓，记录理由，导出选中样本并查看审计时间线 | 交接记录 |
| 换表校准 | 新旧湿度计同抄读数去重，前段估偏差、末段核验，失效房转人工复测，更正后作废受影响预测 | 校准记录 |

## 换湿度计校准口径

更换库房湿度计时，新旧两表只并行同抄若干班，规则如下：

- **同班只算一次**：同一库房同一班次端点的双表读数按一次同抄处理，重复录入先去重。
- **前段估偏差、末段核验**：用前段同抄的「旧表−新表」平均差作为偏差，至少留一个末段班次独立核验；留不出核验班次（同抄不足两班）即转人工复测。
- **两个百分点限值**：末段任一核验班的残差（该班旧−新差值与估计偏差之差）超过 2 个百分点，该库房判定失效，转人工复测，不做自动更正。
- **换算到旧表尺度**：核验通过的库房，最后一次同抄之后的新表读数按「新表读数 + 偏差」平移到旧表尺度后再计算湿度变化与预测；同抄班次与换表前历史读数保持原值。
- **预测作废与重算**：每次校准保存一份分房结论快照。训练或发报用过旧口径的待排班预测标记为「待重算」并按新读数重算；未涉及换表的库房与其它数据版本的计算单不受影响，照常排班。
- **巡查页标注**：待人工复测的库房在换表校准页、结果页和巡查签交页统一标出，且不参与自动优先排序。


## 算法及口径

**滞后岭回归与逐班滚动回测**。每个库房以连续 8 小时交班湿度、本班湿度差、室外湿度和累计开门时间构成滞后特征，并使用目标端点时刻的周期项。输入可完全在预测发布时取得。前半段班次开始训练，后半段每三个班次扩窗回测，标准化与岭回归在训练窗拟合；留出窗内逐班公布一步预测、更新特征可用读数。对照最新湿度基线，以相同样本 MAE 选型。输出下一端点预计相对湿度、与阈值的差及巡查顺序；缺班、重复端点或各库房最新交班时间不齐，应补齐再跑。回测比较用于当前数据选型，未作为另一块外部验证。

录入参数 **排班湿度阈值（%）**，默认 62，允许范围 40–80。预测湿度达到或高于阈值时进入优先巡查；阈值仅影响派班分类。

演示集 `藏丘地下一层_CQ_20261125_交班湿度簿.csv` 由 `backend/src/business/demo.py` 用固定数据或固定随机种子生成。工作台保留每次运行使用的输入版本、参数、结果和签审人。业务判断由服务端执行，前端图表直接读取返回的数值。

## 一天的工作剧本

1. 08:00 六个库房完成本班交接，确认 C02 地图长卷本班累计开门 42 分钟。
2. 08:05 班长导入藏丘地下一层_CQ_20261125_交班湿度簿.csv，核对 246 条读数和 8 小时端点。
3. 08:10 查到最晚端点为 2026-11-25 08:00，下一端点为同日 16:00。
4. 08:15 用 62% 湿度排班阈值运行，查看滞后回归和最新读数基线的滚动 MAE。
5. 08:20 领走优先巡查的 C02 地图长卷任务，C06 包装底片保持常规巡查。
6. 08:30 导出 16:00 下一端点巡查队列，保管员在现场读数后回填班簿。

## 快速启动

```sh
test -f .env || cp .env.example .env
docker compose config --quiet
docker compose up -d --build --wait
docker compose exec -T backend python -m scripts.seed_demo
```

前端在 `http://127.0.0.1:18326`，API 文档在 `http://127.0.0.1:19326/docs`，数据库绑定 `127.0.0.1:17826`。重复运行种子命令保留已有账号和版本。测试验收后用 `docker compose down` 停机可保留数据卷。重置本地演示数据可用 `docker compose down -v --remove-orphans`。

## 技术与配置

| 服务 | 技术与职责 |
|---|---|
| frontend | HTML/CSS/JS ES 模块，Nginx 静态页面与同源 API |
| backend | Python 3.11、FastAPI、SQLAlchemy、JWT |
| worker | Python 后台进程，使用 DB 的原子认领、租约与重试，输出 CSV |
| db | PostgreSQL 16，存账号、版本、计算单和审计 |
| redis | Redis 7，通知 worker 尽快拾取，任务状态由数据库持久化 |

`FRONTEND_PORT`、`BACKEND_PORT`、`DB_PORT` 管理回环端口，`JWT_SECRET` 为签名密钥，`DB_PASSWORD` 为应用数据库口令，`COMPOSE_PROJECT_NAME` 控制该栈的命名空间。

本地 Python 开发可用 `docker compose up -d db` 启动关系库，并另起一个仅绑定回环的 Redis。Compose 内的 Redis 通过容器网络连接。用 Python 3.11 安装 `backend/requirements.txt` 后，进入 backend 目录，设置 `DATABASE_URL`、`REDIS_URL`、`JWT_SECRET`、`ARTIFACTS_DIR`、`SEED_DEMO`，分别运行 `uvicorn src.main:app --reload`、`python -m src.worker`。ARTIFACTS_DIR 需已存在且由两进程共享。前端可使用 Compose Nginx 镜像并重建以加载修改，或用已有 Nginx 反向代理本地 Python 端口。

`backend/src/business/` 保存本题字段、生成器和算法，`backend/src/services/` 处理资源生命周期，`backend/migrations/` 是初始关系模式，`frontend/src/` 按页面、API、会话、组件、路由及样式组织。前后端枚举分别在 `backend/src/constants/workflow.py` 和 `frontend/src/constants/enums.js`。角色用于 JWT 路由与表单权限，计算状态用于队列与结果页，签审决定用于交接页、审计和签发导出。
